## Полученный результат

Реализован React-клиент учебного API с загрузкой, изменением данных и корректной обработкой асинхронных состояний. Приложение:

- получает задачи и категории с сервера через `GET /api/tasks` и `GET /api/categories`;
- передаёт фильтры в query-параметрах (`q`, `completed`, `priority`, `categoryId`) — фильтрация выполняется на сервере;
- создаёт, редактирует, переключает статус и удаляет задачи через `POST`/`PATCH`/`DELETE`;
- после каждой успешной мутации выполняет новый `GET` с актуальными фильтрами;
- различает загрузку, пустой успешный ответ и ошибку;
- сохраняет последний успешный снимок при ошибке обновления;
- отменяет ненужные запросы и игнорирует запоздавшие ответы;
- блокирует повторную мутацию немедленно, до первого `await`;
- сохраняет черновик формы при неуспешной записи;
- проходит 52 автоматические проверки и ручной протокол.

**Ограничения хранения:** данные хранятся в памяти процесса API. Пока работает тот же процесс, обновление страницы не сбрасывает задачи. Перезапуск API или `POST /api/debug/reset` возвращает исходный набор (12 задач). БД отсутствует. `meta.total` — число задач после серверных фильтров, а не размер всей базы; в интерфейсе подписано как последняя полученная выборка.

## Архитектура

**Разделение слоёв:**

- **`src/api-client.js`** — транспорт: `requestJson`, `AbortController`, тайм-аут, преобразование HTTP/сетевых/форматных ошибок в `ApiError` с полями `kind`, `status`, `code`, `details`; `204 → null` без `response.json()`.
- **`src/task-api.js`** — предметный API: `loadInitialData(filters, { signal })`, `createTask(value, { signal })`, `updateTask(id, value, { signal })`, `setTaskCompleted(id, completed, { signal })`, `deleteTask(id, { signal })`, `resetDemoData({ signal })`. Проверяет схемы ответов через `isTask`/`isCategory`.
- **`src/config.js`** — создаёт `api` вне компонента (стабильная ссылка), читает `VITE_API_URL`.
- **`src/hooks/useTaskData.js`** — основное задание: загрузка, очистка, мутации, блокировка, разделение ошибок.
- **`src/App.jsx`** — вызывает `useTaskData({ api, filters })`, хранит снимок редактируемой записи (чтобы смена фильтра не стирала черновик), связывает компоненты.
- **Компоненты** — `TaskForm` (`await onSave(value)`, блокировка при `pending`, сохранение черновика при `false`), `TaskFilters` (управляемые поля фильтров), `TaskList` (последняя полученная выборка).

**Хук `useTaskData` — состояние:** `snapshot`, `status` (`loading`/`ready`/`error`), `error`, `mutationError`, `pending`, `revision`. **Служебные `useRef`:** `mountedRef` (признак монтирования, StrictMode-совместимость), `mutationControllerRef` (немедленная блокировка и отмена текущей мутации).

**Зависимости эффекта загрузки:** `api`, `filters.q`, `filters.completed`, `filters.priority`, `filters.categoryId`, `revision`. `snapshot` и результаты запроса в них не входят — иначе бесконечная загрузка.

**Cleanup:** в каждом цикле создаётся свой `AbortController` и локальный `active`. В cleanup сначала `active = false`, затем `controller.abort()`. Отдельный cleanup `mountedRef` дополнительно отменяет текущую мутацию при размонтировании.

## Загрузка и изменения

**Старые ответы.** Для каждого цикла загрузки — свой `AbortController` и локальный `active`. В `cleanup`: сначала `active = false`, затем `controller.abort()`. Перед записью успеха и ошибки проверяется `active`; в `catch` дополнительно `!controller.signal.aborted`, чтобы отмена не показывалась как ошибка. Отмена не заменяет проверку `active`: тестовая реализация может проигнорировать `signal`, и запоздавший ответ всё равно не попадёт в состояние. В StrictMode дополнительный цикл setup → cleanup → setup отменяет пробный GET; актуальный принимается.

**Повторная мутация.** В `mutate(operation)`: проверка `mountedRef.current`, затем немедленная блокировка через `mutationControllerRef.current` до первого `await` (state `pending` для этого недостаточно — два синхронных вызова увидят прежнее значение). Затем создаётся свой `AbortController`, `setPending(true)`, `setMutationError(null)`, `await operation({ signal })`. При успехе — `setRevision(prev => prev + 1)` → эффект делает новый `GET` с актуальными фильтрами. В `finally` освобождается **только свой** контроллер (`if (mutationControllerRef.current === controller)`) и снимается `pending`.

**Ошибки POST/PATCH/DELETE и последующего GET** разделены:

- `mutationError` — ошибка записи; `error` — ошибка чтения; они не смешиваются.
- Ошибка POST не отменяет уже полученный снимок; ошибка GET не превращает успешный POST в неуспех.
- Если POST подтверждён, а повторный GET упал — `mutationError` остаётся `null`, `error` выставлен, `status = 'error'`, снимок сохранён.
- Автоматического повторного POST нет: после тайм-аута сервер мог сохранить запись, повтор создал бы дубликат.

**Черновик формы.** `TaskForm` вызывает `await onSave(value)`. При `false` черновик сохраняется, `mutationError` показывается пользователю, блокировка снимается. При `true` форма очищается (создание) или выходит из режима редактирования. Смена фильтра не стирает черновик: `App` хранит снимок редактируемой записи, а не ищет её в текущей выборке.

## Контрольные вопросы

1. **Зачем для загрузки нужен эффект, а не запрос в теле компонента?** Тело компонента вызывается при каждом рендере, и запрос выполнялся бы многократно. `useEffect` синхронизирует компонент с внешней системой и умеет очистку.
2. **Когда React вызывает cleanup?** Перед повторным запуском эффекта при изменении зависимостей и при размонтировании компонента.
3. **Почему callback эффекта не объявляется `async`?** Тогда он возвращал бы `Promise`, а React ждёт функцию очистки. Асинхронная функция объявляется внутри и вызывается отдельно.
4. **Какие зависимости нужны загрузке и почему в них нет `snapshot`?** `api`, `q`, `completed`, `priority`, `categoryId`, `revision`. `snapshot` — результат загрузки; его включение вызвало бы бесконечный цикл.
5. **Почему стабильная ссылка на `api` важна?** Новый объект в каждом рендере запускал бы новый GET. `api` создаётся в `config.js` вне компонента.
6. **Зачем кроме `AbortController` проверять актуальность ответа?** Отмена может быть проигнорирована (тестовая реализация, кэш); запоздавший результат всё равно нельзя записывать в состояние.
7. **Почему защита от устаревшего результата нужна и в `catch`?** Отменённый запрос часто бросает ошибку; без проверки она попадёт в `error` и покажется пользователю.
8. **Что проверяет дополнительный цикл StrictMode?** Что эффект корректно очищается и не оставляет утечек; пробный GET отменяется и не влияет на состояние.
9. **Почему одной переменной `pending` в state недостаточно для двух синхронных вызовов?** Оба вызова видят прежнее значение до перерисовки. Нужна немедленная блокировка через `useRef` до первого `await`.
10. **Что означает `true` от `saveTask`, если повторный GET завершился ошибкой?** Мутация подтверждена сервером; ошибка GET — отдельная (`error`), `mutationError` остаётся `null`.
11. **Почему нельзя автоматически повторять POST после тайм-аута?** Сервер мог сохранить запись; повтор создаст дубликат. Нужно сначала обновить список.
12. **Почему смена фильтров не должна отменять мутацию?** Чтение и запись — независимые операции; отмена записи потеряла бы подтверждённое изменение. Для них разные контроллеры.
13. **Что происходит с серверной операцией после отмены клиентского ожидания?** Она может завершиться; отмена клиентского ожидания не является откатом. Следующий GET отразит серверное состояние.
14. **Чем `meta.total` отличается от общего числа записей на сервере?** `meta.total` — число задач после серверных фильтров; общий размер системы он не отражает.
15. **Какие сценарии не проверяются jsdom и требуют браузера?** Браузерный CORS, реальный ввод формы, внешний вид, Network throttling, поведение DevTools — они в ручном протоколе.

Реализован `useTaskData` с эффектом загрузки на стабильных зависимостях, отменой через `AbortController` и проверкой актуальности в обеих ветках запроса, немедленной блокировкой мутации через `useRef`, разделением ошибок чтения и записи, повторным GET с актуальными фильтрами. Исправлены ошибки по ходу работы: отмена текущей мутации при размонтировании через cleanup `mountedRef`, проверка `active` и в `then`, и в `catch`, освобождение в `finally` только своего контроллера (завершение старого вызова не затирает новый). Все 52 проверки пройдены (23 API, 14 интеграционных, 15 React), сборка успешна, ручной протокол и сценарий варианта 3 совпали в dev и preview. При замене учебного API собственным сервером (ПР9–ПР10) потребуется сохранить контракт: те же методы и пути, тот же формат ошибок `{ error: { code, message, details } }`, схему задачи и `204` на DELETE; клиентский код (`api-client`, `task-api`, `useTaskData`) менять не придётся.
